# iPaper 1.12.1 — 额度边界修复（时间增额、部署上限、重译计划、实际用量）

已发布并固定摘要部署；正式复核结果在发布后补记，两个 Worker 未重建。

源码提交 `d8748f0`，平台 `linux/amd64`。

## 为什么发补丁

1.12.0 的独立复核（`.devnotes/ipaper-1.12.0-review.md`）确认四类边界缺陷，本轮逐项修复行为并把这些复现纳入常驻回归。

## R1 仅延长时间也能继续；时间耗尽不再被判为可续跑

- 续跑计划的**时间维度独立判定**：有计划中工作且累计时间已用满时，`resume-plan` 返回 `sufficient=false`、`time.exhausted=true`、`overage.seconds.required = 已用+1`（明确是下限，不是剩余耗时估计）。
- `POST …/resume` 在时间耗尽且仍有工作时拒绝入队（`budget_time_exhausted`，带 `minimum`），不会入队后立刻再次超时；**只调整小时数**即可继续，其他维度不必改动，累计用量不清零。
- 前端 `ResumeBudget` 的"是否确有变化"改为同时考虑四个维度（此前遗漏 `seconds`，导致只延长小时数时按钮仍禁用），并显示"累计执行时间已用完（X 分钟 / 上限 Y 分钟）"。
- 反向情况同样修正：检查点显示已无待发请求时，续跑只做发布，**不因时间耗尽失败**——服务端把状态/取消检查（`check_status`）与执行时间检查（`check`）分离，逐块循环中只在真正需要工作时才检查时间。

## R2 所有预算路径都受部署上限约束

- `IPAPER_TRANSLATION_MAX_*` 明确是**最大值**。校验改为作用于**最终合成额度**：默认、空预算、部分字段、显式预算四条路径逐维度比对上限。
- 上限低于内置默认值时，有效默认值被压到该上限（启动日志说明，预览返回 `defaultCappedByCeiling`），因此不会出现"上限 100、默认 500 仍准入"；显式超限返回 `invalid_budget` 并指出维度；合成结果异常超限时返回 500 类 `invalid_budget_configuration` 而不是静默通过。

## R3 单块重译的续跑计划与执行一致

- `resume_plan` 与执行侧使用相同的重译语义：`force=True`（`kind == 'retranslate'`），旧的成功译文不再被当作"本次重译已完成"，当前任务已保存的**有效子单元**仍从估算中扣除。预览与执行对同一块给出相同的请求数。

## R4 实际用量按输入/输出分别记完整性

- `actual_usage` 分别统计输入与输出的完整性（`inputComplete`/`outputComplete`、`inputMissingAttempts`/`outputMissingAttempts`）；只有两个维度都有合法供应商数据才 `complete`。单项缺失显示未知/部分统计，未按 0 记，也未改变事前预留计数或推断未计费。
- 任务详情分别显示两个维度的缺失次数，只有完整时才说"输入与输出都有供应商数据"。

## 回归与测试修正

- 复核的四项私有复现已纳入 `tests/test_translation_budget.py`（降上限默认准入、时间耗尽不足与拒绝入队、重译计划与执行一致、单项用量不完整），并按修复后的契约补充：放宽上限后较小范围可准入、四条预算路径都受上限约束、无待发请求时耗尽时钟仍能完成发布、五种 supplier 用量形状的逐维完整性、零请求与进行中请求。
- 修正复核指出的两处弱断言：截图量级执行改用**真实预扣**的计数假模型（`ReservedModel.calls == usage.requests` 且 `200 ≤ requests ≤ 245`），"低于已用量"分支改用两请求的任务真正走到。
- `tests/test_daily_scheduler_state.py` 改为由运行时日期推导期望（此前硬编码日期，穿越"今天"后会误判）。
- 浏览器套件新增 R1 回归：耗尽时间的任务只把累计小时数从 1 改到 4、其余维度不动即可提交并保存成功。

## 限制与回退

- 时间维度只能判断"是否已耗尽"，无法预估剩余时长；额度仍是准入上限，不承诺必然完成。
- 回退基线 **Web 1.12.0 ＋ Workers 1.2.0**；本轮无 schema 改动，回退只切镜像。
