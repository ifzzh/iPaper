# iPaper 1.12.0 — 结构化翻译额度：更大默认值、可调整上限与增额续跑

已发布并固定摘要部署；正式只读复核与浏览器验收结果在发布后补记，两个 Worker 未重建。

源码提交 `494cca0`，平台 `linux/amd64`。

## 为什么做这一轮

用户在结构化翻译里选了 15 页 / 271 块 / 0 块可复用，页面估算 245 次请求、273,044 输入、247,782 输出 token，被 **应用自己的 200 次请求上限**挡住（不是供应商余额）。旧实现把默认值和上限写成同一个常量，API 只能降低不能提高；旧任务又保存了独立的 `budget_json`，续跑入口不接受新额度，所以"只改常量"也修不了旧任务。

## A. 让正常整篇翻译可用

| 项目 | 原默认＝硬上限 | 新默认（整篇翻译） | 部署上限（可配置） |
|---|---:|---:|---:|
| 模型请求 | 200 | **500** | **2,000** |
| 输入 token 保守预留 | 500,000 | **1,000,000** | **5,000,000** |
| 输出 token 预留 | 250,000 | **500,000** | **2,000,000** |
| 累计执行时间 | 2 小时 | **4 小时** | **12 小时** |

- 默认值、部署上限、任务已确认额度三者分离：`default_budget(kind)`、`budget_ceiling(kind)`、`ProcessingJobs.budget(value, kind)`。仅 `translate`、`parse_translate`、`retranslate` 使用新值；**概览、深度解读、分析导出、划词翻译与纯解析（MinerU）保持 200/50 万/25 万/2 小时**，API 也无法调大。
- 部署上限可用 `IPAPER_TRANSLATION_MAX_REQUESTS`、`IPAPER_TRANSLATION_MAX_INPUT_TOKENS`、`IPAPER_TRANSLATION_MAX_OUTPUT_TOKENS`、`IPAPER_TRANSLATION_MAX_SECONDS` 覆盖；非正整数配置**启动即失败**，不静默夹取。
- 估算与提交使用同一份已确认额度；页码、语言、解析版本或额度改变都会重新估算，预览过期、估算未就绪或输入非法时不能提交。
- 超出时返回并显示**具体维度**（所需 vs 当前额度）与一键"使用所需额度"；估算分别给出基础请求、允许的 429 重试余量与两者之和，不再把重试上限称作"最多请求数"。
- 任务详情把"已预留"（按字节与生成上限的保守预扣）与"供应商实际用量"分开显示，缺失的实际用量计为缺失、不补零。
- 保留单请求 120 秒、SDK 重试关闭、全局并发 2、每 owner 一个活动任务、队列/文件配额、取消与防重复提交。

## B. 让已创建任务能正确继续

- 已保存任务沿用原 `budget_json`，启动时不批量改库、不静默放宽正在执行的任务。
- 新增 `POST /api/processing/jobs/<id>/resume-plan`（只读）：返回已用量、剩余范围估算（应用单元检查点，已完成的块与子单元不重复计费）与所需额度、部署上限。
- `POST /api/processing/jobs/<id>/resume` 新增可选 `budget`：校验 CSRF、owner、任务类型、状态与部署上限，**不得低于已用量**，新额度是整个任务的累计总额；变更与排队在同一事务内完成，并记录 `budget_adjusted` 事件（前后额度）。重复点击不会重复排队（`job_not_resumable` / `user_processing_busy`）。
- 解析前尚无可靠估算时如实说明；解析后超预算保留解析结果，展示新范围与额度调整入口，等用户明确继续。未知模型结果仍需明确确认，未知 MinerU 创建仍不可重提。
- 不带 `budget` 的 `resume` 保持原行为，概览/解读/划词等类型不受影响。
