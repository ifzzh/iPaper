# iPaper 1.13.5 — 冲突决定的修订来源与保存状态自愈

已发布并固定摘要部署；正式镜像验收结果在发布后补记，两个 Worker 未重建。

源码提交 `133d0cd`，平台 `linux/amd64`。

## 为什么再发一个补丁

1.13.4 之后对**已发布镜像自带前端**复跑镜像验收：V1/V3/V5 通过，V2「保留服务器版本」方向仍失败（点击后服务器端冲突仍未解决），V1 的收尾状态显示"未保存的修改"（服务器与编辑器其实都已是最新正文）。逐步骤诊断后确认两处原因：

1. **面板级冲突提示的决定没有带上编辑器所见的修订**：`NoteConflictBanner` 的按钮调用父级决定接口时未传 `revision`，父级只能用自己 state 里的 note 修订，可能已经过期 → 服务端按"过期决定"拒绝，冲突保持未决。编辑器内的按钮则因携带了它捕获的修订而正常。
2. **保存状态没有自愈**：重复保存或迟到响应之后，客户端认为正文未保存，而服务器已经持有同一正文——界面因此停在"未保存的修改"。

## 修了什么

- **决定绑定的修订优先级**：`revision` 依次取"调用方传入（编辑器捕获的所见修订）→ 编辑器当前待决冲突的修订 → 本页 note 的修订"；只有都未知时才先重新拉取一次笔记。不再用可能过期的 state 静默降级。
- **编辑器上报待决冲突**（`onConflictChange`），两个阅读器共享同一份 `liveNoteConflict`，因此面板级入口与编辑器内按钮的决定语义完全一致。
- **保存状态自愈**：当服务器正文与编辑器正文完全一致、且没有待决冲突/决定时，编辑器直接进入「已保存」（清掉草稿与待发保存），不再对服务器已持有的正文显示"未保存"。
